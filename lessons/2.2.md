# Power Query: интеграция и автоматическое обновление данных

На занятии 2.1 мы построили воспроизводимую последовательность очистки одной выгрузки. Теперь задача становится ближе к реальной отчетности: источников несколько, данные поступают отдельными файлами, справочные сведения находятся в других таблицах, а структура источника может меняться без согласования с аналитиком.

Главная задача занятия – построить запрос, который:

1. объединяет несколько источников;
2. не теряет факты при присоединении справочников;
3. автоматически подхватывает новые файлы;
4. контролирует полноту справочников;
5. допускает изменение пользовательских параметров без правки кода;
6. при изменении структуры источника либо продолжает работать корректно, либо останавливается явно.

> [!NOTE]
> Материалы занятия представлены архивом. До начала работы архив необходимо распаковать. Папка `Выгрузки` первоначально содержит три файла. Файл `Продажи_2026_04 (добавить позже).xlsx` должен находиться **вне** папки `Выгрузки` и добавляется только в разделе о контроле изменения структуры.

## 1. Разбор домашнего задания занятия 2.1

Критерий качества запроса из предыдущего занятия:

**переключение источника на следующую выгрузку не должно требовать ручной правки шагов.**

Перед переходом к новой теме проверим четыре типичных проблемы.

### Новый месяц остался отдельным столбцом

Причина – использована команда:

```text
Отменить свертывание столбцов
```

вместо:

```text
Отменить свертывание других столбцов
```

В первом случае запрос запоминает конкретные месяцы, существовавшие при его создании. Новый период не входит в этот список.

Во втором случае фиксируются идентифицирующие столбцы, а все остальные автоматически переводятся в длинный формат.

### Фильтр итоговых строк не сработал

Если промежуточные итоги удалялись путем снятия флажков с конкретных известных значений, новый регион может пройти фильтр.

Устойчивое условие:

```text
Торговая точка не начинается с "Итого"
```

### Даты преобразовались частично

Если локаль не указана, текстовые даты могут интерпретироваться по правилам другой страны.

Особенно опасна ситуация, когда часть дат преобразуется без ошибки, но неверно.

Например, строка:

```text
03.04.2026
```

может быть прочитана не как 3 апреля, а как 4 марта.

Ошибку получат только значения, которые вообще невозможно интерпретировать в выбранной локали. Остальные могут выглядеть корректно.

> [!WARNING]
> Ошибка преобразования заметна. Молчаливо неверно преобразованная дата опаснее, потому что внешне выглядит допустимой. Локаль следует задавать явно даже тогда, когда часть значений «и так работает».

### Порядковый номер даты

Значение вида:

```text
45717
```

может быть порядковым номером даты Excel.

Это число, а не текстовая дата. Его следует сначала интерпретировать как число, а затем привести к типу «Дата».

## 2. Добавление запросов: append

Power Query поддерживает два принципиально разных способа объединения таблиц.

Короткое правило:

> **Добавление увеличивает число строк. Слияние увеличивает число столбцов.**

### Когда используется добавление

Добавление подходит, если таблицы имеют одинаковую структуру и содержат разные наборы строк.

Примеры:

- продажи за январь + продажи за февраль;
- данные нескольких подразделений;
- последовательные периоды одного реестра.

Содержательно задача звучит:

**«Собрать вместе записи из нескольких одинаковых таблиц».**

### Добавление в существующий запрос и в новый

В Power Query доступны два варианта:

- «Добавить запросы»;
- «Добавить запросы в новый».

В курсе предпочтителен второй вариант.

Исходные запросы остаются самостоятельными, а новый запрос отвечает только за объединение. Если логика объединения окажется неверной, исходные объекты не придется восстанавливать.

### Столбцы сопоставляются по названиям

Это важное свойство append.

Power Query ориентируется не на положение столбца, а на его имя.

Если первая таблица содержит:

```text
Сумма
```

а вторая:

```text
Сумма продаж
```

Power Query не обязательно остановится с ошибкой.

Он может создать два разных столбца:

```text
Сумма
Сумма продаж
```

и заполнить каждый только в соответствующей части строк.

> [!WARNING]
> Несовпадение схем при append может привести не к явному отказу, а к неполным данным. Это один из наиболее опасных типов проблем: запрос завершился успешно, но информация распределилась по разным столбцам.

### Практика

1. создайте запросы к двум месячным выгрузкам;
2. выберите «Добавить запросы в новый»;
3. убедитесь, что строки обеих таблиц присутствуют в результате;
4. сравните наименования столбцов источников.

```quiz
question: Какое правило помогает выбрать между добавлением и слиянием запросов?
A: Добавление увеличивает число строк, слияние – число столбцов
B: Добавление применяется только к Excel, а слияние – только к CSV
C: Добавление всегда требует справочник, а слияние – никогда
D: Слияние увеличивает число строк, добавление – число столбцов
correct: A
explanation: Append собирает однотипные записи вертикально. Merge сохраняет факты и добавляет к ним поля из другой таблицы.
```

## 3. Слияние запросов: merge

Месячная выгрузка содержит факты продаж:

- дату;
- код точки;
- код категории;
- количество;
- сумму.

Но в ней нет, например:

- полного наименования торговой точки;
- региона;
- формата;
- товарной группы.

Эти сведения находятся в справочниках.

Задача merge – присоединить к каждой фактической записи соответствующие атрибуты по ключу.

### Базовый порядок

1. создайте запрос к справочнику;
2. в запросе продаж выберите «Главная» → «Объединить запросы»;
3. выберите второй запрос;
4. укажите ключевой столбец в обеих таблицах;
5. выберите тип соединения;
6. выполните слияние;
7. разверните вложенный столбец кнопкой с двумя стрелками.

При развертывании полезно снять флажок:

```text
Использовать исходное имя столбца как префикс
```

Иначе вместо:

```text
Регион
Формат
```

будут созданы наименования вида:

```text
Точки.Регион
Точки.Формат
```

Формально это работает, но усложняет дальнейшее чтение и сопровождение.

## 4. Типы соединений

Power Query предлагает несколько типов join.

### Левое внешнее соединение

Возвращаются:

- все записи левой таблицы;
- найденные сведения из правой.

Если соответствия в справочнике нет, факт сохраняется, а присоединяемые поля становятся пустыми.

Это основной рабочий вариант для присоединения справочника к фактам.

### Правое внешнее соединение

Сохраняются все записи правой таблицы.

В прикладной работе используется реже. Если для обычного присоединения справочника понадобился right join, следует проверить, не перепутаны ли таблицы местами.

### Полное внешнее соединение

Сохраняются все записи обеих таблиц.

Подходит для сверки двух источников, когда ни один из них нельзя считать главным.

### Внутреннее соединение

Остаются только строки, для которых соответствие найдено с обеих сторон.

Для отчетности по фактам это опасный вариант.

Если код факта отсутствует в справочнике, соответствующая продажа просто исчезает.

> [!WARNING]
> Внутреннее соединение не является «неправильным». Оно делает именно то, что задано. Риск возникает тогда, когда аналитик не осознает, что несопоставленные факты будут отброшены без сообщения об ошибке.

### Левое анти-соединение

Возвращает записи левой таблицы, которым **не нашлось** соответствия в правой.

Используется как средство контроля полноты справочника.

### Правое анти-соединение

Возвращает позиции правой таблицы, которые не используются в левой.

Может применяться для поиска неиспользуемых позиций справочника.

## 5. Контроль количества строк после слияния

После каждого merge необходимо проверить число строк.

Если до присоединения было 78 строк, после обычного левого внешнего соединения также должно остаться 78.

Три варианта:

**Количество уменьшилось**

Вероятная причина – внутреннее соединение. Часть фактов потеряна.

**Количество увеличилось**

Вероятная причина – дубликаты ключа в справочнике.

Если одна точка встречается в справочнике дважды, каждая фактическая строка этой точки после merge размножится на два совпадения.

Это приводит, например, к искусственному увеличению выручки без единой ошибки Excel.

**Количество не изменилось**

Это необходимый, хотя и не единственный, признак корректного присоединения справочника к фактам.

> [!NOTE]
> Контроль количества строк после merge выполняет для операций интеграции ту же функцию, что контрольная сумма для расчетной модели: он позволяет быстро обнаружить потерю или размножение фактов.

Перед присоединением справочник следует проверять на уникальность ключа и при необходимости устранять дубликаты.

### Слияние по нескольким столбцам

Иногда одного ключа недостаточно.

Например, план продаж определяется одновременно:

- кодом точки;
- месяцем.

Тогда в окне merge необходимо выбрать оба столбца с удержанием `Ctrl`.

Порядок выбора должен быть одинаковым в обеих таблицах.

Если сверху выбрано:

1. Код точки;
2. Месяц;

то снизу порядок должен быть таким же.

Иначе Power Query может не найти совпадений и вернуть пустые значения без явной ошибки.

### Практика

1. создайте запрос к справочнику точек;
2. выполните левое внешнее соединение;
3. разверните наименование и регион;
4. отключите префиксы;
5. сверьте число строк до и после merge.

```quiz
question: После левого внешнего соединения справочника количество строк выросло с 78 до 84. Что в первую очередь следует проверить?
A: Локаль числовых столбцов
B: Наличие дубликатов ключей в справочнике
C: Наличие null в фактах
D: Режим автоматического пересчета Excel
correct: B
explanation: При нескольких совпадениях в правой таблице одна строка фактов размножается. Рост числа строк после left join является важным сигналом дубликатов по ключу.
```

## 6. Анти-соединение как постоянный контроль

Левое внешнее соединение сохраняет факты без соответствия, но после merge они выглядят как обычные строки с пустыми справочными полями.

На десятках тысяч строк такие случаи легко пропустить.

Поэтому контроль следует сделать постоянным.

### Построение контрольного запроса

1. дублируйте запрос фактов;
2. снова выполните merge с соответствующим справочником;
3. выберите **«Анти-соединение (левое)»**.

Результат будет содержать только записи, для которых соответствия нет.

В учебных данных ожидаются:

- 3 записи с кодом точки `TT09`;
- 3 записи с кодом категории `CAT7`.

Итого:

```text
6 несопоставленных записей
```

### Что делать с найденными записями

Сам анти-join не решает предметную проблему.

Возможны разные причины:

- появилась новая торговая точка;
- справочник не обновлен;
- в коде опечатка;
- в выгрузку попали чужие данные.

Решение о корректировке принимает владелец данных.

Задача аналитика – обеспечить, чтобы расхождение не осталось незамеченным.

> [!NOTE]
> Анти-соединение для справочников – аналог контрольной суммы для модели. Ноль строк означает отсутствие несопоставленных записей; ненулевой результат требует разбирательства.

Контрольный запрос рекомендуется сохранять в книге постоянно и выводить либо на отдельный лист, либо как заметный показатель количества строк.

### Практика

Постройте анти-соединение по справочнику точек и категориям и определите состав несопоставленных записей.

## 7. Импорт всех файлов папки

Один из основных сценариев Power Query:

1. каждый месяц приходит отдельный файл;
2. файлы помещаются в одну папку;
3. итоговый запрос должен автоматически объединять все периоды.

### Импорт папки

Выполните:

1. «Получить данные»;
2. «Из файла»;
3. «Из папки»;
4. укажите папку `Выгрузки`;
5. выберите «Объединить и преобразовать данные»;
6. в качестве объекта образца выберите лист `Данные`.

Power Query создаст несколько связанных объектов.

### Образец файла

Содержит ссылку на один файл, используемый как образец структуры.

### Функция «Преобразовать файл»

Это функция, которая принимает очередной файл и применяет к нему последовательность преобразований.

### «Преобразовать образец файла»

Это главный объект для настройки обработки **одного файла**.

Именно здесь выполняются:

- удаление служебных строк;
- поднятие заголовков;
- удаление преждевременной типизации;
- очистка сумм;
- преобразование с учетом локали.

### Основной запрос

Применяет функцию ко всем файлам папки и объединяет полученные таблицы.

> [!WARNING]
> Преобразования, которые должны выполняться отдельно для каждого файла, настраиваются в запросе **«Преобразовать образец файла»**, а не только в основном объединенном запросе.

### Контрольный показатель

При исходных трех файлах:

- файлов – `3`;
- строк в каждом – `26`;
- итоговых строк – `78`.

### Source.Name

При импорте из папки Power Query добавляет поле:

```text
Source.Name
```

Не следует удалять его без необходимости.

Оно позволяет:

- установить файл-источник каждой строки;
- использовать имя файла как элемент аудита;
- извлекать период, если он зашит в имени файла.

Например:

```text
Продажи_2026_01.xlsx
```

можно разделить по символу `_` и получить год и месяц.

### Фильтрация содержимого папки

Power Query пытается обработать все файлы папки.

Поэтому непосредственно после шага источника следует отфильтровать:

- `Extension` – оставить только ожидаемое расширение, например `.xlsx`;
- `Name` – исключить временные файлы Excel, имя которых начинается с `~$`.

Иначе случайный документ или временный файл может остановить обновление.

### Организация запросов

Когда запросов становится много, применяются два правила.

**1. Не все запросы нужно загружать на лист.**

Справочники, служебные объекты и промежуточные запросы можно загружать как:

```text
Только создать подключение
```

**2. Запросы следует группировать.**

Например:

```text
Источники
Справочники
Результат
```

Это перенос принципа архитектуры книги на уровень Power Query: объекты разделяются по назначению и получают осмысленные имена.

### Практика

Импортируйте папку, настройте обработку образца и убедитесь, что основной запрос содержит **78 строк**.

```quiz
question: Где следует выполнять очистку, которая должна применяться отдельно к каждому новому файлу при импорте папки?
A: Только в основном объединенном запросе
B: В запросе «Преобразовать образец файла»
C: На листе Excel после загрузки
D: В контрольном анти-соединении
correct: B
explanation: Преобразование образца становится основой функции, применяемой к каждому файлу папки, включая будущие файлы.
```

## 8. Параметры запроса

В построенном запросе остается архитектурный дефект: путь к папке может быть записан непосредственно в шаге источника.

Например:

```text
C:\Курс\Выгрузки\
```

Если книгу передать коллеге с другим расположением файлов, запрос перестанет работать.

Это тот же дефект, который на занятии 1.1 рассматривался для изменяемой константы внутри формулы.

### Встроенные параметры Power Query

Можно использовать:

```text
Главная → Управление параметрами → Создать параметр
```

У параметра задаются:

- имя;
- тип;
- значение.

Это уже лучше жесткой строки внутри шага, но значение параметра изменяется через редактор Power Query.

### Параметры на листе

Для пользовательской книги удобнее хранить изменяемые параметры в таблице Excel.

Например:

```text
Параметр                    | Значение
Путь к папке выгрузок       | C:\Курс\Выгрузки\
Отчетный год                | 2026
Минимальная сумма           | 100000
Регион                      | Все
```

Таблица превращается в источник Power Query.

Пример M-выражения для получения значения:

```m
Параметры{[Параметр="Путь к папке выгрузок"]}[Значение]
```

Содержательно эта запись означает:

**найти строку таблицы параметров с нужным названием и вернуть значение из соответствующего поля.**

Пользователь меняет путь или другой параметр на листе, не редактируя шаги запроса.

### Параметр – это не только путь

Таким способом можно управлять:

- отчетным годом;
- минимальной суммой;
- регионом;
- другими фильтрами загрузки.

Это прямое продолжение архитектуры предпосылок:

- на первом дне предпосылки управляли расчетами;
- здесь параметры управляют загрузкой и подготовкой данных.

> [!WARNING]
> При работе с несколькими источниками Power Query может показать предупреждение об уровнях конфиденциальности. В учебной среде проверка может быть отключена по указанию преподавателя. В рабочей книге не следует отключать ее автоматически без понимания причины и характера объединяемых источников.

### Практика

1. создайте запрос к таблице параметров;
2. получите значение пути;
3. замените жестко записанный путь в шаге источника ссылкой на параметр;
4. проверьте обновление.

## 9. Контроль изменения структуры источника

Теперь добавим в папку файл:

```text
Продажи_2026_04
```

В апрельской выгрузке схема изменена.

Вместо:

```text
Код точки
Сумма
```

используются:

```text
Точка
Сумма продаж
```

Шаги запроса продолжают обращаться к старым именам, поэтому запрос останавливается.

### Явный отказ лучше молчаливого искажения

На первый взгляд остановка запроса – недостаток.

Но сравните два сценария.

**Сценарий 1. Запрос остановился**

Пользователь видит ошибку и начинает диагностику.

**Сценарий 2. Запрос продолжил работать**

Из-за несовпадения названий Power Query создал дополнительные столбцы, часть данных оказалась пустой, а итоговый отчет собрался с неполными суммами.

Второй вариант гораздо опаснее.

> [!NOTE]
> Полностью защититься от изменений источника невозможно. Цель устойчивого решения – не обязательно продолжить работу любой ценой, а сделать так, чтобы изменение структуры приводило к **явному контролируемому отказу**, а не к тихому искажению результата.

### Меры защиты

В зависимости от характера источника могут применяться разные приемы.

**Переименование столбцов сразу после источника**

Подходит, если порядок столбцов стабилен, а внешние названия могут меняться.

**Проверка состава столбцов**

Отдельный контрольный запрос получает перечень фактических названий и сравнивает его с ожидаемой схемой.

**Обработка отсутствующего столбца**

Некоторые операции можно настроить так, чтобы отсутствие поля не останавливало запрос.

Этот прием требует особой осторожности: допустимое отсутствие должно быть действительно предусмотрено предметной логикой. Иначе явная ошибка превращается в молчаливую потерю данных.

### Практическое правило

При изменении структуры важно сначала решить:

**должен ли запрос продолжить работу или должен остановиться?**

Для критичных полей чаще безопаснее явный отказ.

## 10. Язык M и пользовательские функции

Раздел носит обзорный характер.

Каждое действие Power Query фактически является M-кодом.

Весь запрос можно увидеть через:

```text
Главная → Расширенный редактор
```

Упрощенный пример:

```m
let
    Источник = Excel.Workbook(File.Contents(Путь)),
    Данные = Источник{[Item="Данные"]}[Data],
    Заголовки = Table.PromoteHeaders(Данные)
in
    Заголовки
```

### Конструкция let ... in

В блоке `let` объявляется последовательность именованных шагов.

Каждый следующий шаг может ссылаться на предыдущий.

После `in` указывается объект, который является итоговым результатом запроса.

Эта конструкция по смыслу близка функции LET, изученной в Excel:

- объявляются промежуточные именованные результаты;
- итогом является выбранное выражение.

### Пользовательские функции

При импорте из папки автоматически создается функция:

```text
Преобразовать файл
```

Она:

- принимает файл;
- применяет последовательность шагов;
- возвращает обработанную таблицу.

Собственные функции Power Query строятся по тому же принципу.

На базовом уровне курса требуется уметь **читать общую структуру** M-запроса. Написание пользовательских функций вручную относится к повышенной сложности.

## Использование ИИ: анализ M-запроса и логики объединения

Языковая модель может помочь разобраться в сложном M-коде, но особенно полезно просить ее не просто «объяснить код», а проверить риски интеграции данных.

Пример запроса:

```prompt
Ниже приведен M-код Power Query:

[ВСТАВЬТЕ M-КОД]

Проанализируй его как процедуру интеграции данных.

1. Перечисли источники и последовательность шагов.
2. Для каждого merge укажи:
   - левую и правую таблицы;
   - ключи;
   - тип соединения;
   - какие строки могут быть потеряны или размножены.
3. Для каждого append укажи, какие названия столбцов должны совпадать.
4. Найди жестко заданные пути, годы, регионы и другие изменяемые значения, которые можно вынести в параметры.
5. Укажи шаги, чувствительные к переименованию или исчезновению столбцов.
6. Предложи контрольные проверки:
   - количество строк;
   - anti join;
   - проверка состава столбцов;
   - количество null после слияния.
7. Если предлагаешь изменить код, не меняй смысл обработки и отдельно перечисли проверки эквивалентности.
```

Результат ИИ является гипотезой для проверки, а не готовым исправлением.

После изменения запроса необходимо самостоятельно проверить:

1. число строк до и после merge;
2. число строк после append;
3. состав несопоставленных записей;
4. отсутствие дубликатов по ключам справочников;
5. работу на новом файле периода;
6. соответствие контрольных сумм исходным данным.

## 11. Итоги занятия

После занятия необходимо зафиксировать семь положений:

1. Добавление увеличивает число строк, а слияние – число столбцов.
2. Append сопоставляет поля по наименованиям; несовпадение схем может привести к неполным данным без явной ошибки.
3. Основной тип для присоединения справочника к фактам – левое внешнее соединение; внутреннее соединение молча отбрасывает несопоставленные факты.
4. Анти-соединение является постоянным контролем полноты справочников.
5. При импорте папки обработка каждого файла настраивается в «Преобразовать образец файла».
6. Изменяемые пути и другие параметры не должны быть зашиты в запрос – их следует выносить в параметры, доступные пользователю.
7. Защита от изменения структуры источника состоит не в том, чтобы запрос никогда не останавливался, а в том, чтобы критичные изменения становились явными и не приводили к молчаливому искажению данных.

Контрольные показатели учебных материалов:

- файлов в папке `Выгрузки` – **3**;
- строк в каждом исходном файле – **26**;
- строк после объединения – **78**;
- записей с кодом точки `TT09` – **3**;
- записей с кодом категории `CAT7` – **3**;
- anti join по обоим справочникам – **6 записей**;
- строк после корректного левого внешнего соединения – **78**;
- строк после внутреннего соединения со справочником точек – **75**.
